Structured Products: Data Quality Investigation¶

Analyst objective: assess daily SIX structured-product snapshots, explain quality exceptions, and demonstrate traceable change monitoring for an SRP-style data operation.

Data are real exchange CSVs, not synthetic market records. Unit-test fixtures are hand-made and never included in this analysis. This is independent portfolio work, not an SRP database replica or an endorsement.

Questions: Which mandatory fields fail? Are spikes persistent or transient? Which changes suggest lifecycle events? What can we responsibly report from the available data?

1. Inspect the source before judging quality¶

Files contain two header blocks and a production-time footer. A naive CSV load counts these as products. Missing intraday high/low fields may mean no trading, rather than a data defect. First/last trading dates are not necessarily issue/maturity dates.

2. Daily quality objectives and anomaly detection¶

Project-defined targets: product-type completeness >=99.5%, mapped issuer code >=99%, zero critical failures, and >=95% records without critical/high failures. These are not Derivia contractual SLAs. No processing latency or cost SLA can be measured from source snapshots alone.

3. Investigate missing classification spikes¶

Use historical SCD versions, not the latest product classification, to attribute exceptions to the issuer code available on that day. Inspect the next available snapshot to see whether values recovered; recovery is not proof of a manual correction.

missing = query("SELECT snapshot_date, COUNT(*) AS missing_type FROM qc_results WHERE rule_id='R05' GROUP BY 1 ORDER BY 1")
baseline = missing.missing_type.median()
spikes = missing[missing.missing_type > baseline*3]
display(spikes)
issuer_spikes = query("""SELECT q.snapshot_date, h.issuer_code, COUNT(*) AS missing_type
 FROM qc_results q JOIN product_history h ON q.isin=h.isin
 AND q.snapshot_date>=h.valid_from AND (h.valid_to IS NULL OR q.snapshot_date<h.valid_to)
 WHERE q.rule_id='R05' GROUP BY 1,2 ORDER BY 1,3 DESC
""")
display(issuer_spikes[issuer_spikes.snapshot_date.isin(spikes.snapshot_date)])
for day in spikes.snapshot_date:
    next_day = snapshots.loc[snapshots.snapshot_date > day, 'snapshot_date'].min()
    recovery = query("""SELECT COUNT(*) AS affected,
        COUNT(m.isin) AS still_present_next_day,
        COUNT(m.isin) FILTER (WHERE q2.isin IS NULL) AS no_longer_missing_next_day
        FROM qc_results q
        LEFT JOIN daily_market m ON q.isin=m.isin AND m.snapshot_date=?
        LEFT JOIN qc_results q2 ON q.isin=q2.isin AND q2.snapshot_date=? AND q2.rule_id='R05'
        WHERE q.rule_id='R05' AND q.snapshot_date=?
    """, [next_day.date(), next_day.date(), day.date()])
    display(Markdown(f'### Spike on {day:%Y-%m-%d}'))
    display(recovery)

4. Audit trail and lifecycle signals¶

NEW_LISTING means first observed after the baseline; REMOVED means absent from the next available snapshot. Neither establishes issuance or formal delisting. Reference-data changes are audited separately from daily market-price movements. SCD validity windows are [valid_from, valid_to).

Analyst conclusion and handover¶

  • Preserve raw snapshots and capture source links/checksums. Never silently repair identifiers or infer payoff terms from short names.
  • Classification-completeness spikes warrant source investigation. Investigate adjacent-day recovery and issuer concentration before assigning root cause.
  • Separate confirmed failures (invalid identifier, duplicate key, missing required type) from information/review flags (numeric geography, trade inactivity, provisional mappings).
  • Review observed termination-date changes against notices before calling them knock-outs or autocalls.
  • The CSV lacks underlying identifiers, coupons, barriers, source issuance volumes, team processing logs and contract costs. Those analyses require additional real sources; they are deliberately not fabricated.
  • Tableau-ready CSVs and the Excel exception workbook are generated by python -m srp_dq.report. The operating procedure is in docs/SOP.txt.
